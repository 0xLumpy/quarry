## Release contract

`v0.3.10` is an integrity release, not a feature release. It must establish that Quarry:

1. never reports successful acquisition before primary evidence is durably settled;
2. never mutates a sealed base run;
3. never certifies a revision, manifest or campaign outcome it cannot reconstruct;
4. preserves an honest, bounded and replayable disposition for work it could not retain or execute;
5. launches the artifact and credential set that policy actually approved;
6. permits intended private-target, broad-active and public-OOB behavior while withholding scanner,
   metadata and unrelated control-plane destinations;
7. makes private operator output lossless and does not invent conclusions from absent evidence;
8. ships with reproducible, non-live release gates and basic public-project integrity.

No implementation may close a row by reducing the accepted Nuclei request set, default-denying private
targets, disabling public Interactsh, imposing a small universal time limit, or discarding target evidence.

## Required implementation order

This order minimizes transitional formats and makes each gate meaningful:

1. Freeze release inputs and sanitized regression oracles; do not alter source engagement runs.
2. Close `V310-01` and `V310-02` first: evidence settlement and repository authority are prerequisites.
   Their shared implementation contract is
   [`PHASE-1-EXECUTION-REPOSITORY.md`](../design/PHASE-1-EXECUTION-REPOSITORY.md).
3. Build `V310-03` and `V310-04` on that boundary; do not add another sidecar format.
4. Close independent `V310-05` while the state work proceeds.
5. Close `V310-06` and publish the honest supported envelope.
6. Close `V310-07` and `V310-09` without changing the accepted defaults.
7. Close the minimum correctness subset in `V310-08`; keep the larger report redesign deferred.
8. Complete and freeze `V310-10`'s pre-nomination implementation prerequisites, authorize and commit the
   clean `0.3.10` nomination, then run the scope-selected record-producing gates and complete aggregation
   and detached approval against that exact candidate. Formal work-package closure derives from the
   accepted aggregate; the tag and publication receipt follow as `RG09` postconditions.

## Release gate evidence

The canonical definitions, result vocabulary, isolation lanes and evidence schema
are in [`RELEASE-GATES.md`](RELEASE-GATES.md). This ledger only selects which of
those gates apply to `v0.3.10`; it does not elevate the collect-only development
runner or any other partial runner into accepted release evidence.

All evidence must come from one quiescent release-candidate identity whose two
package-version sources equal `0.3.10`. Candidate identity, gate records,
artifacts, aggregate, detached approval and publication receipt are immutable
external objects linked by declared content digest; a URL, CI job or
documentation row is only a locator or projection. A commit message, partial
rerun, skipped prerequisite, historical engagement run or command printed in
documentation is not release evidence. Each scope-selected pre-aggregate record
slot begins `OPEN` and remains blocking until the accepted aggregate selects a
schema-valid record and verified artifacts. `E-AGGREGATE` and `E-APPROVAL` also
begin `OPEN`, but deterministic aggregation and the later detached signature
establish them; neither is selected as an input record by the aggregate.

The aggregate contains every scope-selected Phase A-C record, all four Phase D
records, and the `E-DOCS`, `E-PROJECT-HYGIENE` and pre-publication
`E-ARTIFACTS` records. A Phase D record is `pass` or `blocked` when live
execution is required (or `fail` for a violated assertion), and each of the four
is an exact `not_applicable` record when the approved scope omits live execution.
The aggregate does not contain an `E-AGGREGATE` record or its own digest, and it
precedes the detached `E-APPROVAL`. Successful deterministic aggregation
establishes `E-AGGREGATE`; the later valid signature establishes `E-APPROVAL`.
The signed tag then targets the exact candidate commit, the already-attested
artifact bytes are published, and a publication receipt binds the tag and
promoted digests.

`A-EVIDENCE-SCHEMA` requires a hermetic aggregator-conformance/golden-vector
result and its canonical digest. That prerequisite proves deterministic
aggregator behavior; it is not the candidate release aggregate.

## Nomination, version and publication rule

The current tree stays at `0.3.9`, **NO-GO**, until all intended source changes,
scope, schemas, validation inputs, thresholds, supported matrix and candidate
release notes are frozen and the maintainer explicitly authorizes nomination.
That authorization permits one dedicated nomination commit to change both
package-version sources to `0.3.10`. It does not close a work package or gate,
create a tag, authorize publication or turn the decision green.

Accepted release evidence is collected only after that commit, against its
quiescent candidate identity. Before tagging or publishing, all of the following
must be true:

- every in-scope work package, including the pre-publication acceptance scope
  of `V310-10`, is closed by the accepted aggregate;
- every scope-selected aggregate-input gate record is `pass` or validly
  `not_applicable` for that exact candidate;
- all deferred limitations are accurately represented in the accepted
  release-note artifact;
- no unresolved stop-ship row remains in the candidate-bound current-head
  audit input;
- candidate-built package and provenance subjects have verified accepted
  digests; and
- the maintainer's detached approval binds the aggregate digest.

The signed `v0.3.10` tag must target the nominated candidate commit. Publication
must promote the exact accepted artifact bytes and retain a digest-bound receipt;
it must not rebuild from a later documentation or version commit. Any tracked
change outside designated non-authoritative projection/index fields after
nomination creates a new candidate and repeats every affected gate.

The exact signed tag and publication receipt then satisfy the remaining `RG09`
postconditions and may be mirrored in the post-publication `V310-10`
documentation projection. They are not inputs to the aggregate, approval or
pre-tag `V310-10` acceptance and therefore cannot block their own creation.

After acceptance, a descendant commit may reconcile this ledger and related
indexes as a documentation-only projection. It must cite the candidate commit,
tree and identity digest; the aggregate and approval digests; the signed-tag
object identity; and the publication-receipt digest. It must not alter the
candidate's frozen scope and is never the release subject or evidence authority.
Until the nomination prerequisites above are met, `v0.3.10` remains a plan and
the package remains `0.3.9`.
