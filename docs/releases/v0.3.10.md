## Release contract

`v0.3.10` is an integrity release, not a feature release. It must establish that Quarry:

1. never reports successful acquisition before primary evidence is durably settled;
2. never mutates a sealed base run;
3. never certifies a revision, manifest or campaign outcome it cannot reconstruct;
4. preserves an honest, bounded and replayable disposition for work it could not retain or execute;
5. launches the artifact and credential set that policy actually approved;
6. permits intended private-target, broad-active and public-OOB behavior while withholding scanner,
   metadata and unrelated control-plane destinations;
7. makes private operator output lossless and does not invent conclusions from absent evidence;
8. ships with reproducible, non-live release gates and basic public-project integrity.

No implementation may close a row by reducing the accepted Nuclei request set, default-denying private
targets, disabling public Interactsh, imposing a small universal time limit, or discarding target evidence.

## User-facing release summary

### Behavioral changes

The planned release makes execution settlement, repository mutation, revision
publication, campaign truth, runtime identity and network effects explicit and
fail closed. It does not broaden Quarry's target or feature scope.

### Accepted risks

Raw same-UID mutation outside Quarry's authenticated repository operations is
outside the cooperative authority boundary. The larger indexed report/database
redesign and distributed execution remain deferred under the constraints below.

### Known limitations

No public release or distribution claim is being made. Production trust policy,
public signing keys, signature roles/thresholds/rotation, detached approval,
signed tagging, publication receipts, and CI-image attestation are
`not_applicable_until_publish`. The current source intentionally remains
version `0.3.9`. Resource-performance limits are measured and recorded but do
not block this milestone; integrity outcomes collected by those gates do.

### Migrations

No blanket data-format migration is promised. Unknown or unsupported manifests
fail closed; operators should retain prior runs and use a new output root when
validating the nominated package.

### Exit and result contract

Success is reported only after the primary process, streams, descendants and
durable evidence have settled. Empty, partial, timed-out and refused work retain
typed outcomes rather than being reclassified as successful completion.

### Supported matrix

The milestone matrix is Linux on the Python versions actually exercised by the
maintainer and GitHub CI. Exact observed interpreter, local/CI environment,
isolation profile, managed tool, template version, and content-digest identities
come from the support matrix. A runner image is an observed environment label,
not an attested VM identity.

## Required implementation order

This order minimizes transitional formats and makes each gate meaningful:

1. Freeze release inputs and sanitized regression oracles; do not alter source engagement runs.
2. Prove the minimum `V310-08` correctness subset in actual rendered output before collecting further
   gate evidence: absence must not become a WAF/origin claim, and private output must not omit a store
   observation or its material/artifact digests.
3. Close `V310-01` and `V310-02`: evidence settlement and repository authority are prerequisites.
   Their shared implementation contract is
   [`PHASE-1-EXECUTION-REPOSITORY.md`](../design/PHASE-1-EXECUTION-REPOSITORY.md).
4. Build `V310-03` and `V310-04` on that boundary; do not add another sidecar format.
5. Close independent `V310-05` while the state work proceeds.
6. Close `V310-06` and publish the honest supported envelope.
7. Close `V310-07` and `V310-09` without changing the accepted defaults.
8. Finish the internal evidence/sign-off projection for `V310-08`; keep the larger report redesign deferred.
9. Complete and freeze `V310-10`, run the applicable gates on one clean,
   quiescent `0.3.9` tree across the actual local/Linux-CI matrix, verify their
   content-bound evidence, and record the maintainer sign-off. No version bump,
   production trust policy, detached approval, or publication step is required.

## Internal milestone completion rule

The tree stays at package version `0.3.9`. Completion requires the scoped
integrity implementations, frozen inputs/corpus identities, managed tool and
output receipts, applicable fault checks, repository seal, actual support
matrix, and one clean local/Linux-CI result set. Resource benchmark values are
recorded for review without becoming blockers. The maintainer's ledger sign-off
closes the internal milestone.

Production signing policy, detached approval, signed tags, and publication
receipts are deferred until Quarry is published, gains a second maintainer, or
is operated as a service. Dormant schemas and verification code are retained,
but are not wired into `v0.3.10` completion.

The following publication procedure is retained for that future trigger and is
not applicable to the current milestone.

For a future published release, accepted distribution evidence is collected
only after its dedicated nomination commit, against that quiescent candidate
identity. Before tagging or publishing, all of the following must be true:

- every in-scope work package, including the pre-publication acceptance scope
  of `V310-10`, is closed by the accepted aggregate;
- every scope-selected aggregate-input gate record is `pass` or validly
  `not_applicable` for that exact candidate;
- all deferred limitations are accurately represented in the accepted
  release-note artifact;
- no unresolved stop-ship row remains in the candidate-bound current-head
  audit input;
- candidate-built package and provenance subjects have verified accepted
  digests; and
- the maintainer's detached approval binds the aggregate digest.

The signed `v0.3.10` tag must target the nominated candidate commit. Publication
must promote the exact accepted artifact bytes and retain a digest-bound receipt;
it must not rebuild from a later documentation or version commit. Any tracked
change outside designated non-authoritative projection/index fields after
nomination creates a new candidate and repeats every affected gate.

The exact signed tag and publication receipt then satisfy the remaining `RG09`
postconditions and may be mirrored in the post-publication `V310-10`
documentation projection. They are not inputs to the aggregate, approval or
pre-tag `V310-10` acceptance and therefore cannot block their own creation.

After acceptance, a descendant commit may reconcile this ledger and related
indexes as a documentation-only projection. It must cite the candidate commit,
tree and identity digest; the aggregate and approval digests; the signed-tag
object identity; and the publication-receipt digest. It must not alter the
candidate's frozen scope and is never the release subject or evidence authority.
Until the nomination prerequisites above are met, `v0.3.10` remains a plan and
the package remains `0.3.9`.
